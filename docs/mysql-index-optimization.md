# MySQL 索引与分页优化记录

## 1. 测试环境

- MySQL 8
- 数据量：100000 条
- 部门数量：50
- 状态数量：3

## 2. 联合索引分析

现有索引：

`(department_name, status, created_at)`

### 2.1 部门 + 状态 + 时间排序

结论：完整匹配联合索引，无需 `filesort`。

### 2.2 只有状态

结论：跳过了原联合索引的最左列，无法高效利用该索引。

新增索引：

`(status, created_at, id)`

### 2.3 只有部门 + 时间排序

结论：可以使用 `department_name` 筛选，但由于跳过中间的
`status`，无法直接利用 `created_at` 完成整体排序，仍然需要
`filesort`。

## 3. 覆盖索引与回表

### 3.1 `Using index`

`key` 表示优化器最终选择的索引。

`Extra` 中的 `Using index` 表示使用了覆盖索引，即查询所需字段 都能从索引中取得，无需回表。

### 3.2 回表

通过二级索引找到主键 ID 后，再根据主键到聚簇索引中读取完整记录。

## 4. 深分页对比

### 4.1 OFFSET 分页

- 扫描：30010 行
- 返回：10 行
- 耗时：约 28.7 ms

OFFSET 分页需要扫描并丢弃前 `offset` 条记录，因此扫描量约为：

`offset + limit`

### 4.2 游标分页

- 扫描：10 行
- 返回：10 行
- 耗时：约 0.465 ms

游标分页从上一页的边界位置继续扫描。本次测试约提升 62 倍。

若存在额外过滤条件，实际扫描量仍可能大于 `LIMIT`。

## 5. 游标分页的限制

- 不适合直接跳转到任意页。
- 通常不提供传统的准确页码体验。
- 必须使用稳定、唯一的排序，例如 `created_at + id`。
- 并发新增数据时，相比 OFFSET 更不容易发生重复或遗漏。

## 6. 总结

- 联合索引需要结合查询条件和排序字段设计。
- `Using index` 表示覆盖索引，并不只是“使用了索引”。
- 深分页的成本会随着 OFFSET 增大。
- 大数据量连续翻页更适合使用游标分页。
