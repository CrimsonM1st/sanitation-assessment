# MySQL 事务、MVCC 与锁实验

## 1. 实验环境

- MySQL 8.4
- Docker
- Navicat
- InnoDB

## 2. REPEATABLE READ 快照读

记录三次结果：

- 第一次普通 SELECT：null
- B 更新并提交：88
- 第二次普通 SELECT：null
- SELECT ... FOR UPDATE：88

结论：普通 SELECT 是快照读，FOR UPDATE 是当前读。当前读读取记录的最新可见版本，并根据操作添加相应锁；如果目标记录被其他事务持锁，当前读可能等待。

## 3. READ COMMITTED

- 第一次查询：89
- B 更新并提交：90
- 第二次查询：90

结论：RC 下每条查询读取执行前已经提交的数据，可能发生不可重复读。

## 4. 行锁阻塞

记录：

- A 使用 FOR UPDATE 锁定记录
- B 更新同一记录时等待
- A 提交后 B 自动完成，影响1行

## 5. 死锁实验

记录循环等待过程：

A 持有 id1，等待 id2  
B 持有 id2，等待 id1

结果：

- B 收到 1213
- B 自动回滚并释放锁
- A 继续执行

```sql
SHOW ENGINE INNODB STATUS;
```

可以通过 `LATEST DETECTED DEADLOCK` 查看参与事务、持有的锁、等待的锁以及被回滚的事务。

结论：本次实验中 B 被选择为牺牲事务；MySQL 不保证每次都回滚 B，通常会选择回滚成本较低的事务。

## 6. 死锁预防

- 统一加锁顺序，例如始终按 ID 从小到大加锁
- 缩短事务时间
- 减少锁定范围
- 为查询建立合适索引
- 对死锁进行有限重试

## 7. 总结

- 快照读依赖 MVCC，不主动加行锁
- 当前读读取最新可见版本，并根据具体操作添加相应锁
- RR 通过一致性读视图，解决普通快照读场景下的不可重复读
- RC 能读取其他事务最新提交的数据
- COMMIT 和 ROLLBACK 都会释放事务持有的锁
